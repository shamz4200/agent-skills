# $shamz Cross-Channel Learnings Board

A $shamz method for harvesting lessons from every chat, verifying each one against its source, filing it dated on a shared board, and folding the durable ones into the rules. Method only: the board entries themselves are private house rules and must never ship as-is. Use generic example entries only, or none.

## Purpose

- Any channel chat or worker can drop something learned during the day that could benefit the others. Anyone can also just talk, with no agenda.
- No production work, no approvals, and no publication binds happen on the board. It is a conversation space, not a build space.
- Channel chats cannot post here directly; learnings get relayed by the main agent or workers. Post them short: what was learned, which channel, why it matters to others.
- Anything that earns standing-rule status still gets folded into the shared rules the same night. The board is the casual share; shared memory is the durable record.

## Harvest

1. Collect learnings from every chat: production chats, review chats, and the main chat.
2. For each learning, record what was learned, who learned it, which channel, and why it matters to the others.
3. Relay each learning the same day it lands. Never hold a relay until the end of the week.
4. Cross-channel transfers are always attributed to who learned it and which channel, never presented as the relaying agent's own idea.

## Verify

- Learnings must be retrieved or verified, never invented.
- Before filing, check each learning against its source: the chat, the file, the log, or the live platform state it came from.
- A learning that cannot be verified is not filed as a lesson. Record it as unverified, or leave it out and note the gap.
- Label claims by confidence where they rest on memory: verified from inspected evidence, retrieved from memory or documents, inferred from reasoning, hypothesis needing testing, or unknown. Never present an inference as a verified fact.

## File dated board entries

- File each verified learning as one dated board entry: date and time, source chat, what was learned, why it matters to others.
- Entries are appended in order. Never edit a past entry in place; a correction is a new dated entry.
- The board is the lounge's memory. New drops get added the same day.
- Generic example entries only, when an example is needed:
  - "Verify packaging landed, don't just confirm the plan: check each item live on the platform before reporting it done."
  - "Fix, then report: don't bring clips that need fixing. Fix, re-check every clip for the same defect, harden the check, then report."
  - "When a client secret is lost, rotate it. Don't try to view the existing one."
- Never ship real board entries. Channel names, account decisions, private corrections, and dated house rules stay private.

## Fold into the rules

- When a learning earns standing-rule status, fold it into the rules file the same night. Record its date and source there.
- A weekly review proposes rule changes; it never applies them on its own authority. A rule changes only on $shamz's explicit word.
- Keep the rules file dated and attributed. A newer explicit instruction from $shamz supersedes anything in it; update the file when that happens.

## Weekly review and summary

- Run a weekly review on the same day each week. Its first step is to read the state file and resume any unfinished piece recorded there.
- Each review builds in pieces, in order: board entries, then the rules file, then the weekly-review log entry, then the state file, then the chat summary last. Each piece is written to disk as it lands, verified pieces skipped on rerun, never re-posting a summary already visible in the chat.
- The review reads the week's work, the board, the rules, and the chat for the week, and writes one dated note: what happened, what was learned, what changed in the protected folder, and anything that should carry into next week.
- Deliver a short summary. Quiet only if the week was genuinely empty, and even then, record the note.
- The review itself does not authorise a build, a push, a resume, a tool install, or a payment.

## State file

- Keep a durable state file in the protected folder, never in a temporary folder. It holds the last completed output, the next run date, and the exact resume route.
- After any restart, read the state file first, check which pieces already exist on disk and in the chat, and resume from the first missing piece before reporting status. Never re-do a piece already on disk, and never re-post a summary already visible.
- A manual resume runs only on $shamz's order, and only after checking the state file so it cannot duplicate work already done.

## Rules

- Harvest from every chat, verify against the source, file dated, fold into the rules the same night when it earns standing status.
- Attribute every transfer. Never present another chat's learning as your own idea.
- Method only: real board entries are private house rules and never ship.
- Never invent a learning. An unverified learning is not filed as a lesson.
