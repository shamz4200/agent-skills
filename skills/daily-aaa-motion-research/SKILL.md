# $shamz Daily Motion Research

A $shamz daily research habit: study the best motion websites in the world against a locked design vision, and write down only what is new. Research only. It never builds anything and never pushes anything live.

## When to use it

Use it once a day, at a fixed time. It is a study pass, not a build pass. A research note never resumes a paused project, never changes a locked decision, and never authorises a rebuild.

## Before the first run

1. Lock the design vision in writing: what the finished experience should feel like, its pipeline, its camera language, its performance targets, and its game feel. Keep that vision in one file in your workspace.
2. Verify the vision file's path before every run. Read the vision from the path your README records, not from a dashboard, a summary, or a remembered path. If the recorded path is stale, fix the record first and say so in the note; do not silently research against the wrong vision.
3. Keep a folder of past daily notes, dated, so each new note can be checked against them.

## Run the study

1. Read the locked design vision first.
2. Read the existing research notes, so you know what has already been covered.
3. Search the web for current, sourced techniques and real motion websites. Read the sources, do not summarise a summary.
4. Cover, as relevant that day: render-to-web pipelines and budgets, cinematic camera (spline flights, easing, transitions, wipes, parallax), particle and zone navigation instead of scrolling, calm readable interface design, game feel (motion, sound, progression, loading and arrival beats), performance targets, and real motion sites with what specifically makes each one feel like a game.

## Write delta-only notes

- Write only what is new since the last note. No repeats. If a technique was already filed, do not file it again; link to the earlier note.
- File each technique under one bucket: pipeline, camera, particles, interface, game feel, or budgets. One technique, one bucket.
- Keep the note concise. A daily note is a short brief, not an essay.

## Proven versus speculation

- Split every note strictly into PROVEN and SPECULATION.
- PROVEN means a named source supports it: a documented technique, a live site that does it, or a measured result. Cite the source and its date.
- SPECULATION means an idea, a guess, or something untested. Label it as such, even if it sounds plausible.
- Do not claim a technique works until a source supports it. Do not promote speculation into proven by rewording it.

## End with one testable step

- Every note ends with exactly one concrete next step that could be tested as a small preview first.
- The step must be testable: what would be built, what would be measured, and what result would count as working. A vague "explore this" is not a step.
- The step is a proposal. It does not authorise a build, a rebuild, or a push. Those still need $shamz's explicit order.

## Rules

- Research only. Never start a full rebuild, never push live, never change a locked decision on the strength of a research note.
- Sources and dates on everything. An unsourced technique is speculation, not proven.
- Delta-only: if it is not new, it does not go in the note.
- The vision path is verified before the run, every run. A stale path is fixed in the record, not worked around silently.
